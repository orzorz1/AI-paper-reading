# 代码结构说明

这份文档说明当前项目的代码组织方式，以及每个模块负责什么。

## 1. 目录结构

当前主要目录如下：

```text
src/paper_reading/
  cli.py
  config.py
  errors.py
  llm.py
  logging_utils.py
  models.py
  utils.py
  pipeline/
    parser.py
    layout.py
    matcher.py
    selector.py
    planner.py
    explainer.py
    composer.py
    pdf_exporter.py
    orchestrator.py

tests/
文档/
models/
```

## 2. 入口层

### `cli.py`

这是命令行入口。

当前提供两个命令：

- `build`：处理单篇 PDF
- `batch`：批量处理某个目录下这一层的所有 PDF

它的职责比较简单：

- 读取参数
- 加载配置
- 初始化 orchestrator
- 调用构建流程
- 把结果打印到控制台

这里尽量不放业务逻辑，避免 CLI 和核心流程耦合太深。

## 3. 配置与基础设施

### `config.py`

负责配置读取。

当前支持两种来源：

- `.env`
- 可选 YAML 配置文件

主要配置包括：

- OpenAI 兼容接口
- 版面识别模型
- 输出语言
- 默认输出根目录

### `errors.py`

定义统一异常类型。

这样做的好处是：

- CLI 可以统一捕获业务异常
- 错误提示更清楚
- 测试里也更容易断言失败类型

### `logging_utils.py`

负责日志配置。

当前支持：

- 默认信息级日志
- `--verbose` 时输出更详细日志

### `utils.py`

放共用的小工具函数，例如：

- 路径处理
- 文本截断
- 文件落盘
- 字符串归一化

这些函数本身不直接承载业务含义，只做通用辅助。

## 4. 数据模型层

### `models.py`

这里定义所有核心数据结构，项目内部尽量通过这些模型传递数据，而不是裸字典。

主要模型包括：

- `PaperMetadata`
- `ParsedPaper`
- `ParsedPage`
- `PageTextBlock`
- `PageImageBlock`
- `LayoutRegion`
- `FigureCandidate`
- `SelectedFigure`
- `StoryOutline`
- `FigureExplanation`
- `FinalDocument`
- `BuildOptions`
- `BuildResult`

这样做的好处是：

- 每一步输入输出更清晰
- 结构更稳定
- 后续加字段时不容易把别的地方弄坏

## 5. 流水线模块

### `pipeline/parser.py`

负责 PDF 解析。

主要工作：

- 用 `PyMuPDF` 读取 PDF
- 提取全文和每页文本
- 提取文本块和图片块
- 渲染页面图
- 自动抽取标题和摘要

这是整个流程的起点。

### `pipeline/layout.py`

负责版面识别。

当前封装的是 `DocLayout-YOLO`。

它对外只暴露一个主要能力：

- 输入页图
- 输出统一格式的 `LayoutRegion`

内部还处理了：

- 本地权重路径加载
- Hugging Face repo 加载
- 模型坐标到 PDF 坐标的映射

### `pipeline/matcher.py`

负责把 caption、编号、版面区域和真实图块匹配起来。

这是最偏“规则”的模块。

主要工作：

- 找 caption
- 归一化图编号
- 给候选图打分
- 选择最优候选
- 裁出最终图片

这个模块的目标是把“Fig1 到底是哪张图”尽量做准。

### `pipeline/selector.py`

负责关键图选择。

它调用文本 LLM，根据论文上下文和候选图信息，选出最值得放进最终阅读材料的图片。

输出是结构化的：

- 图编号
- 选择理由
- 排名

### `pipeline/planner.py`

负责整体阅读结构规划。

它不是最终写作层，而是一个中间层。

主要输出：

- 中文题目
- 一句话总结
- 背景
- 方法核心
- 结果概述
- 图片角色

### `pipeline/explainer.py`

负责逐图解释。

它调用多模态模型，对每张关键图分别生成：

- 图标题
- 图表达什么
- 图怎么读
- 图为什么重要

### `pipeline/composer.py`

负责最终 Markdown 生成和兜底修正。

当前做两件事：

1. 组织输入，把上下文、图和结构化结果交给 LLM 直接写 Markdown
2. 对 LLM 输出做少量后处理，例如：
   - 补头部
   - 补漏掉的图
   - 规范缩写解释
   - 统一标题格式

这里还保留了一个规则渲染路径，可用于 fallback 和测试。

### `pipeline/pdf_exporter.py`

负责把最终 Markdown 导出成 PDF。

这是一个轻量导出器，不依赖浏览器渲染。

当前支持：

- 标题
- 小标题
- 段落
- 引导块
- 列表
- 图片

并且做了一些排版优化：

- 小标题和正文层级更清楚
- 列表逐条渲染
- 中英混排断行更自然

### `pipeline/orchestrator.py`

这是整个项目的总编排器，也是最关键的模块。

它负责把前面所有模块串起来，形成一条完整流水线。

大致顺序是：

1. parse
2. layout detect
3. match figures
4. select figures
5. plan story
6. explain figures
7. generate markdown
8. export pdf

如果你想理解整个项目先后顺序，先看这个文件最有效。

## 6. LLM 层

### `llm.py`

这里封装了 OpenAI 兼容 API 调用。

主要职责：

- 统一请求格式
- 支持文本输出
- 支持结构化 JSON 输出
- 处理超时、502、429 等失败
- 自动重试

这样上层模块就不需要直接处理 `httpx` 细节。

## 7. 测试结构

### `tests/`

测试按模块拆开，主要包括：

- `test_cli.py`
- `test_config.py`
- `test_llm.py`
- `test_parser.py`
- `test_layout.py`
- `test_matcher.py`
- `test_composer.py`
- `test_orchestrator.py`
- `test_pdf_exporter.py`

测试的作用不是“证明论文真的读懂了”，而是防止你改代码时把这些基础行为改坏：

- CLI 是否还能正常调用
- 配置是否还能正确读取
- 重试是否还能生效
- 图匹配有没有回归
- Markdown / PDF 生成有没有被破坏

## 8. 代码阅读建议

如果你第一次看这个项目，建议顺序如下：

1. `README.md`
2. `src/paper_reading/cli.py`
3. `src/paper_reading/pipeline/orchestrator.py`
4. `src/paper_reading/models.py`
5. 依次看各个 pipeline 模块

如果你只想改某一块，可以这样找：

- 改标题/摘要解析：看 `parser.py`
- 改版面识别模型：看 `layout.py`
- 改图匹配：看 `matcher.py`
- 改选图策略：看 `selector.py`
- 改写作风格：看 `planner.py`、`explainer.py`、`composer.py`
- 改 PDF 样式：看 `pdf_exporter.py`
- 改批量逻辑：看 `cli.py`

## 9. 当前代码特点

这套代码目前的特点是：

- 模块职责比较单一
- 流程比较清晰
- 中间产物保存完整
- 适合继续迭代 prompt、选图策略和 PDF 样式

它不是一个大而全的平台，更像一条明确、可维护的处理流水线。
