# 项目流程说明

这份文档描述的是当前项目已经实现的真实流程，不是规划中的理想流程。

## 1. 输入

工具支持两种输入方式：

- 单篇：输入一个 PDF 路径
- 批量：输入一个目录，处理该目录下这一层的所有 `.pdf`

可选参数：

- `--title`：手动覆盖论文标题
- `--abstract`：手动覆盖摘要
- `--max-figures`：最多选择几张关键图
- `--verbose`：输出更详细的日志

## 2. 总体链路

当前主流程是：

`PDF 解析 -> 版面识别 -> 图表候选匹配 -> LLM 选图 -> LLM 规划整体结构 -> 多模态 LLM 逐图解释 -> LLM 生成 Markdown -> Markdown 导出 PDF`

## 3. 详细步骤

### 3.1 PDF 解析

工具先用 `PyMuPDF` 读取 PDF，完成这些工作：

- 提取全文文本
- 提取每一页文本块
- 提取每一页原始图片块
- 渲染每一页页面图，供版面识别模型使用
- 自动抽取标题和摘要

这里还做了两个额外处理：

- 标题抽取会尽量避开 `arXiv` 边栏、摘要标题、机构信息等干扰项
- 如果没有标准摘要，会用前几段正文作为 `abstract_fallback_text`

### 3.2 版面识别

每一页渲染图会送入 `DocLayout-YOLO`，识别版面区域。

当前内部统一使用四类标签：

- `figure`
- `table`
- `caption`
- `text`

模型输出的是图片像素坐标，代码会把它映射回 PDF 坐标，这样后面做 caption 匹配和裁图时才能统一使用同一套坐标系。

如果某一页版面识别失败：

- 这一页不会中断整个流程
- 系统会记录 warning
- 后续匹配会尽量退回规则逻辑

### 3.3 图表候选生成与匹配

这一步的目标是把论文里的 `Fig1 / Fig2 / Table1` 和真实图片区域对应起来。

当前做法是“规则优先，模型辅助”：

1. 从文本块里找到像 caption 的内容
2. 抽取并归一化图编号，例如：
   - `Fig. 1`
   - `Figure 1`
   - `FIGURE 1`
   最终都变成 `Fig1`
3. 在同一页的版面区域里寻找最近的 `figure/table`
4. 根据这些信息打分：
   - 垂直距离
   - 水平重叠
   - caption 和图的上下关系
   - 与原始图片块的 IoU
5. 裁出最终图片，保存到 `artifacts/figures/`

这里还处理了一个常见误判：

- 正文里提到的 `as shown in Fig. 1` 不再被当成 caption

### 3.4 选关键图

候选图生成后，系统会优先过滤掉表格，只把 `Fig*` 送给文本 LLM 做关键图选择。

输入给模型的上下文包括：

- 论文标题
- 论文摘要
- 正文主体文本
- 每个候选图的编号、页码、caption

输出是结构化结果：

- 选中了哪些图
- 每张图为什么重要
- 重要性排序

目标不是“挑最漂亮的图”，而是挑最适合帮助读者理解论文的问题、方法和结果的图。

### 3.5 构建整体上下文

在进入写作阶段前，系统会先构造一个较大的论文上下文。

当前不是只喂前几页，而是尽量使用整篇正文：

- 先把全文正文拼出来
- 遇到 `References / Appendix / Supplementary / Acknowledgments` 之后停止
- 尽量排除参考文献和附录

除此之外，还会额外抽出重点章节片段：

- `Introduction`
- `Method`
- `Experiment`

这部分上下文会在后面的整体规划、逐图解释和最终 Markdown 写作里复用。

### 3.6 生成整体阅读结构

文本 LLM 会根据：

- 论文标题
- 摘要
- 去掉参考文献和附录后的正文
- 重点章节摘录
- 已选关键图信息

生成一份结构化阅读骨架，主要包括：

- 中文题目翻译
- 一句话总结
- 研究背景与任务定义
- 方法核心
- 结果概述
- 每张图在文中的角色

这一步不是直接产出最终文档，而是给后续写作提供一个较稳的中间层。

### 3.7 逐图解释

接下来，多模态 LLM 会对每张关键图单独解释。

每次输入包括：

- 论文标题
- 论文摘要
- 全局论文上下文
- 图所在页前后 1 页的局部上下文
- 图编号
- 图角色
- 图 caption
- 裁出来的图片本身

输出包括：

- 图标题
- 图主要表达什么
- 应该怎么读
- 它为什么重要

这一层的作用是把“图”变成可写入最终阅读文档的说明材料。

### 3.8 生成最终 Markdown

现在最终 Markdown 不是规则模板硬拼，而是直接交给 LLM 写。

输入给写作模型的内容包括：

- 标题
- 摘要
- 较大的正文上下文
- 整体阅读结构
- 已选图片顺序
- 每张图的路径、角色、caption、解释

模型输出一份完整 Markdown。随后程序再做少量兜底处理：

- 确保头部一定有：
  - 英文标题
  - 中文标题
  - 一句话总结
- 确保所有已选图片都至少出现一次
- 处理缩写第一次解释、后面只保留缩写
- 规范掉一些头部格式不统一的问题

### 3.9 Markdown 导出 PDF

Markdown 生成完成后，会再自动导出一份 PDF。

当前 PDF 导出器支持：

- 一级标题
- 二级标题
- 普通段落
- 引导块
- 列表
- 图片

导出器还做了这些处理：

- 小标题和正文层级分开
- 列表项逐条渲染，不会挤成一段
- 中英混排时尽量减少英文和数字的异常断行

## 4. 输出结果

默认情况下，输出目录在输入 PDF 所在目录下，目录名格式：

`原pdf名-时间`

例如：

`test-202604012200`

目录中主要包含：

- `paper_readable.md`
- `paper_readable.pdf`
- `artifacts/`

`artifacts/` 里会保存中间结果，方便排查：

- `metadata.json`
- `parsed_paper.json`
- `paper_blocks.json`
- `layout/page_001.json`
- `figure_candidates.json`
- `selected_figures.json`
- `story_outline.json`
- `figure_explanations.json`
- `final_document.json`
- `figures/`

## 5. 批量处理流程

批量命令会：

1. 读取目录下这一层的所有 `.pdf`
2. 按文件名排序
3. 逐篇复用单篇处理流程
4. 输出成功和失败统计

默认行为是：

- 单篇失败不会影响后面的 PDF

如果加了 `--fail-fast`：

- 某一篇失败后会立即停止批量处理

## 6. 当前限制

当前项目有这些边界：

- 只支持 `zh-CN` 输出
- 主要面向常见 AI 论文 PDF
- 目前没有 Web 页面，只有 CLI
- 最终只稳定输出 Markdown 和 PDF
- PPT 还没有接入当前主流程

## 7. 为什么这样设计

这套流程的核心思路是：

- 先用规则和版面模型把“图是谁”这件事做稳
- 再让 LLM 负责“图为什么重要”和“怎么讲清楚”

这样比把所有问题都交给一个大模型更稳，也更容易维护。
